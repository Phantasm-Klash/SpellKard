# 原 TNA 峰值密度在原生客户端的渲染开销（E2E）

2026-11-06，原生 `.exe`（`app-v62`）+ CDP，探针 `dev/danmaku_render_load.mjs`。

## 为什么量 CPU 耗时而不是 FPS

conch 的 rAF 在窗口失焦时会被限到约 30fps；`Laya.Render.predicate = null`、
`frameInterval = 16.67` 已确认**帧率门控未激活**，所以后台测出的 FPS 绝对值
不代表前台表现。`Page.bringToFront` 在 conch 的 CDP 里不支持，系统层置前也被
安全策略拦下，因此改为在 `frameLoop` 回调内直接量「逐帧更新 N 个弹幕实体」的耗时。

## 结果（2 秒窗口，共享 TNA 图集纹理 `ebullet_1.png`，256×256 加载成功）

| 弹幕数 | 帧数 | 每帧更新耗时 avg | P95 | 后台限流下 FPS |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 65 | 0.001 ms | 0.001 ms | 32.4 |
| 200 | 57 | 0.110 ms | 0.211 ms | 28.4 |
| **768（原 TNA 峰值）** | **56** | **0.361 ms** | **0.714 ms** | **27.5** |

60fps 的每帧预算是 16.67 ms：**768 颗的更新开销占 2.2%，P95 也只占 4.3%**。
从 200 → 768 颗只多了 0.25 ms，近似线性且系数很小。

## 结论

**客户端 CPU 侧不是密度瓶颈**。上不了原 TNA 密度（平均 641 颗 vs 线上 28 颗）
不是因为「768 颗会卡」，而是 `boss21_tna` 的实测链表没有接到默认 boss 上
（见 `docs/boss21-tna-wiring.md`）。这条测量把「性能顾虑」从决策里排除了。

## 局限（别过度解读）

- 测的是自造 `Laya.Sprite` 的位置更新循环，**不是** `AtlasBulletRenderer` 的完整路径
  （不含图集帧切片、对象池复用、视口剔除）。
- 不含 GPU 绘制提交；真机 GPU 表现仍需前台录制抽查（沿袭
  `STAGE_PARITY_REPORT.md` §6.3 的遗留项）。
- FPS 列仅作同批次相对参考，窗口在后台，绝对值不可信。
- 与 `dev/stage_parity.mjs` 互补：后者验「渲染是否逐像素忠实」（三条实测 trace
  450/450、0 px），本探针验「这个量级扛不扛得住」。
